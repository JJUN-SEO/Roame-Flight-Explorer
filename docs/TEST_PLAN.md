# Test plan

## 1. Strategy

| Layer | What | How | Runs on |
|---|---|---|---|
| Pure domain | Search, filters, ordering, active filters, aggregation, great-circle, formatting | Table-driven unit tests with no coroutines | `commonTest` (JVM + iOS sim) |
| Data | API client, cache, saved flights, transactions | Ktor `MockEngine` + in-memory or temp-file SQLite | `commonTest` / `jvmTest` |
| Store | Offline state machine, selection, latest-wins, failure messages | Fakes + `runTest` + Turbine | `commonTest` |
| Contract | The real fixture decodes and its facts hold | Read `fixtures/flights.json` | `jvmTest` |
| Platform UI | Rendering, gestures, states | **Manual QA checklist (§5)**, filled in on both platforms | Emulator / simulator |

The brief asks for *focused* shared tests plus a written record of the checks performed on both platforms. Platform UI automation is out of scope unless time allows (see the priority tiers in PLAN).

**Naming.** Prefix each test with the rule ID and use camelCase, so it works on Kotlin/Native: `@Test fun f4_pointsEqualToMax_isIncluded()`.

**Test helpers** live in `commonTest/.../testing/`:

- `flight(id = "x", origin = "BOS", destination = "CDG", date = "2027-02-01", points = 25_000, cabin = "Economy", program = "Avios")`: a builder with sensible defaults.
- `FakeFlightsApi`: a scripted queue of responses or errors, with an optional gate that holds a fetch in flight.
- `FakeSavedFlightsRepository`: saved flights in memory, for V7. It can make writes fail (`failing += Op.Save`), hold a write in flight (`gate`), or report a finished write's change a moment later, as the database does (`holdChanges`, then `publish()`).
- `FakeFlightRepository`: a cache and sync status set by hand, for store tests that want everything on the test dispatcher.
- `awaitState { … }`: waits in real time for a store on a real database to reach a state.
- `TestClock`: a settable `now`.
- `testDb()`: `Room.inMemoryDatabaseBuilder<AppDatabase>()` with the bundled SQLite driver on the JVM, or a temp-file database for the "survives reopen" tests.

## 3. Running tests

```bash
./gradlew :shared:jvmTest
```
```bash
./gradlew :shared:iosSimulatorArm64Test
```
```bash
./gradlew :shared:allTests
```

The second and third commands need a Mac. `allTests` runs every target that is available on the host.

**Android frame timing (Step 6.1).** Started with `-no-window`, the emulator renders with `lavapipe`, a software renderer, so its frame times say nothing about the app (Step 4.8). For timing, start it with a window and `-gpu host`: `dumpsys SurfaceFlinger` then names the Mac's GPU ("Android Emulator OpenGL ES Translator (Apple …)"). Fling with `adb shell input swipe`, read `dumpsys gfxinfo <package>`, and compare with Android's Settings app flung the same way. On the owner's 8 GB Mac, the emulator slows to a crawl once macOS runs out of swap (its load average reached 60), so check `uptime` inside the emulator before trusting a number.

**iOS QA through idb (since Step 5.1, owner's choice).** The simulator has no `adb`, so QA uses Meta's idb 1.7.8 to read the accessibility tree (`idb ui describe-all`) and tap (`idb ui tap x y`, in points). Nothing is installed system-wide: the companion comes from the release's `idb-companion.macos-arm64.tar.gz` (checked against its `.sha256`), and the client wheel goes into a virtual environment on Astral's standalone Python 3.12, because the client needs Python 3.10 or newer and macOS ships 3.9. Notes:
- The iOS 27 tab bar is a small centred capsule, but idb reports the full-width bar as one element, so tap the tabs by position.
- `xcrun simctl launch --console-pty` ends the app when it stops, so give it time.
- SwiftUI's `Slider` doesn't jump to a tap, so drag its thumb with `idb ui swipe`. The calendar's month arrows aren't in the accessibility tree, so tap them by position.
- A `TabView` can leave the hidden tab's elements in idb's tree, and a sheet still sliding up reports moving frames. Check the screen (for example that "Show N flights" is there) before tapping.
- idb can't type accented letters. Put the text on the simulator's clipboard with `xcrun simctl pbcopy`, long-press the field, and tap Paste.
- The Thread Performance Checker only runs from Xcode. From the command line, Xcode's Main Thread Checker can be loaded with `SIMCTL_CHILD_DYLD_INSERT_LIBRARIES=…/usr/lib/libMainThreadChecker.dylib`.
- On the owner's 8 GB Mac, a launch can show a white screen for 10–15 s while macOS swaps. A sample of the app showed UIKit building the tab bar, not our code. Relaunching straight away took about 1 s. Wait for the first frame before judging timing, and don't take a large screenshot file as proof the app is up: the home screen is large too.
- Location: `xcrun simctl location <udid> set 47.6062,-122.3321` sets Seattle (`clear` removes it), and `xcrun simctl privacy <udid> reset location <bundle id>` makes the app ask again. The permission dialog is in idb's tree, so its buttons can be tapped by label. Text typed while the dialog is opening can go to the dialog instead of the field.
- Reduce Motion can be switched with `xcrun simctl spawn <udid> defaults write com.apple.Accessibility ReduceMotionEnabled -bool true` (then `false`), before launching the app.

### 4.1 Scalability benchmarks (Phase 6)

These measure the SCALE-* targets in REQUIREMENTS §11. Record the medians in SUBMISSION_NOTES §6.

- **Synthetic data:** a seeded generator in `jvmTest` (`SyntheticData.flights(count, airports, seed)`) that keeps the fixture's shape: random routes, dates, cabins, programs and points.
- **Cases**, each with warm-up runs and the median of 20 runs:

  | Case | Sizes | Target |
  |---|---|---|
  | `reduce()` (search → filter → sort → aggregate) | 1k / 10k / 100k flights | < 16 ms at 10k |
  | Airport search per keystroke | 32 / 1,000 / 5,000 airports | < 1 ms at 5k |
  | SQLite cache replace (JVM driver) | 10k / 100k rows | < 2 s at 100k |
  | Map aggregation | 100k flights | < 16 ms |
  | Memory: dataset + indexes | 10k / 100k flights | Recorded, not gated |
- **Tooling:** plain timed loops are enough. `kotlinx-benchmark` is optional. JVM numbers are a proxy for devices; spot-check the 10k case on a real phone.

## 6. Failure-injection hooks (debug builds only)

To demo and QA failures without code changes:

- Server: no switches (D25). Stop the API, or turn on airplane mode in the emulator, for a failed request (Q16–Q18). The server rereads its fixture on every request, so edits show up on the next refresh (Q14, Q15, Q19).
  - Don't edit `fixtures/flights.json` (CLAUDE.md). Since Step 4.6, run a copy instead: `./gradlew :server:installDist`, put an edited `fixtures/flights.json` in a scratch folder, and start `server/build/install/server/bin/server` from that folder. The server reads `fixtures/flights.json` relative to where it starts. Only one server can use port 8080.
  - A refresh that hangs, to see the refresh bar (R11) and then a timeout (R10), since Step 5.6: with the API stopped, run `sleep 45 | nc -l 8080`. It accepts the request and never answers. Plain `nc -l 8080` doesn't work in the background: macOS's `nc` closes the connection as soon as its input ends, so the app sees a quick failure instead.
- App: a hidden debug toggle, "Fail next DB write", that makes `SavedFlightsRepository` throw once. This covers Q20 and OFF-8. Strip it from release builds or keep it behind `BuildConfig.DEBUG` / `#if DEBUG`.
  - Built in Step 4.4 as `AppGraph.failNextSavedWrite()`. The next save or remove then fails once, without touching the database.
  - **Android (debug builds only):** select a flight and long-press the card's "Selected flight" title. A snackbar confirms "Debug: the next save or remove will fail."
  - **iOS (debug builds only, Step 5.4):** the same long-press, which reaches the hook through `ExplorerStoreIos.failNextSavedWrite()`. A toast confirms it. With idb, hold for 2 s (`idb ui tap x y --duration 2`); 1.2 s was too short.

## 7. Demo recording script (DEL-4)

Aim for about 4 minutes per platform. Record Android first, then repeat on iOS.

1. **Setup shot:** a terminal running `./gradlew :server:run`, with `curl -s localhost:8080/flights | head` showing the data.
2. **Launch:** a fresh install shows the loading state, which may only flash, then 1,000 flights. Point out the count and the default date range.
3. **Search:** type `" boston "` in From → BOS. Type `tokyo` in To → HND and NRT. Clear both.
4. **Filters:** dates Feb 10 – 12 (call out the inclusive ends), cabin Business, points up to 60k, programs Avios + Aeroplan → show the chips and the count. Clear one chip, then Reset.
5. **Map:** pan and zoom. Tap the Paris marker → sheet → pick a flight → route line + card. Switch to List → the same selection. Apply a filter that removes it → the selection clears.
6. **Save:** save 2–3 flights (from the list and from the map card). Open the Saved tab, change the filters to show it's independent, and remove one.
7. **Offline:** Ctrl‑C the API, then close and reopen the app → stale banner, data intact.
8. **Reopen with the API stopped:** force-quit and relaunch → cached results and saved flights are present. Search still works, and removing a saved flight works.
9. *(Optional)* Start the API again, then reopen the app → the banner clears.
